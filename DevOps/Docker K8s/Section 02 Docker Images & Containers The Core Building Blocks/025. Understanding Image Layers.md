# Docker Image Architecture: Cơ Chế Layer, Caching Và Tối Ưu Hóa Dockerfile

### TL;DR (Tóm tắt nhanh)

Docker Image được xây dựng dựa trên kiến trúc phân lớp (layer-based), trong đó mỗi câu lệnh trong Dockerfile tạo ra một lớp read-only được lưu vào bộ nhớ đệm (cache). Khi rebuild image, Docker sẽ tái sử dụng cache của các lớp không thay đổi, nhưng một khi có một lớp bị thay đổi (ví dụ: code thay đổi), **tất cả các lớp phía sau nó sẽ bị vô hiệu hóa cache và buộc phải chạy lại**, do đó thứ tự sắp xếp câu lệnh trong Dockerfile quyết định tốc độ build nhanh hay chậm.

---

### 1. Khái niệm cốt lõi (Core Concepts)

* **Kiến trúc phân lớp (Layer-based Architecture):** * Mỗi một chỉ thị/câu lệnh (instruction) trong `Dockerfile` (như `WORKDIR`, `COPY`, `RUN`) khi thực thi sẽ tạo ra một lớp vật lý (layer) tương ứng.
* Docker Image thực chất là một tập hợp gồm nhiều lớp này chồng lên nhau theo thứ tự từ trên xuống dưới.


* **Tính chất Read-Only của Image:**
* Khi một image đã build xong, tất cả các layer của nó đều ở trạng thái "bị khóa" (lock) và chỉ đọc (read-only). Không thể sửa đổi nội dung bên trong một image đang có.
* Nếu bạn thay đổi code hoặc cấu hình, bạn bắt buộc phải build lại image (thực chất là tạo ra một image mới hoàn toàn).


* **Cơ chế Caching (Bộ nhớ đệm):**
* Docker tự động lưu lại kết quả thực thi của từng layer sau lần build đầu tiên.
* Nếu bạn rebuild image mà không sửa đổi gì trong cấu hình hoặc file liên quan, Docker sẽ nhận diện được kết quả không đổi và kích hoạt trạng thái `using cache`. Quá trình này diễn ra cực kỳ nhanh (chỉ mất một phần nhỏ của giây).


* **Hiệu ứng Đô-mi-nô khi Invalidate Cache (Hủy Cache):**
* Khi Docker quét các file và phát hiện có sự thay đổi (ví dụ: bạn sửa 1 dòng code ở bước `COPY`), layer đó sẽ bị hủy cache để thực thi lại từ đầu.
* **Quan trọng:** Docker không phân tích sâu xem sự thay đổi đó có ảnh hưởng đến các câu lệnh tiếp theo hay không. Do đó, **ngay khi một layer bị hủy cache, toàn bộ các layer nằm phía sau nó (subsequent layers) cũng sẽ bị hủy cache và bắt buộc phải chạy lại**.


* **Container Layer (Lớp thực thi):**
* Khi bạn khởi chạy một container từ image, Docker sẽ phủ thêm một lớp mỏng gọi là *Container Layer* (hoặc lớp Read-Write) lên trên cùng. Đây là lớp đại diện cho ứng dụng đang chạy (kết quả của lệnh `CMD` hoặc `ENTRYPOINT`).



---

### 2. Tối ưu hóa & Best Practices

* **Chiến lược tách biệt Dependency và Source Code:**
* *Thực tế:* Tần suất thay đổi source code ứng dụng (file `.go`) là rất liên tục, trong khi tần suất thay đổi các thư viện bên thứ ba (`go.mod`, `go.sum`) là rất ít.
* *Giải pháp:* Đưa các câu lệnh copy file quản lý dependency và lệnh tải thư viện lên trước. Sau đó mới thực hiện `COPY` toàn bộ source code còn lại.
* *Kết quả:* Khi bạn sửa code ứng dụng, Docker vẫn giữ được cache của bước tải thư viện (vốn là bước tốn nhiều thời gian nhất), giúp tốc độ build hằng ngày của bạn tăng lên đáng kể.



---

### 3. Ví dụ Dockerfile (Đã chuyển đổi sang Golang)

Dưới đây là cách áp dụng cơ chế tối ưu hóa layer từ bài giảng (vốn dùng `package.json` / `npm install` của Node.js) chuyển sang dự án **Golang** (`go.mod` / `go mod download`).

```dockerfile
# Sử dụng base image của Golang
FROM golang:1.22-alpine

# Thiết lập thư mục làm việc bên trong container
WORKDIR /app

# ==========================================
# BƯỚC TỐI ƯU HÓA LAYER: QUẢN LÝ DEPENDENCY
# ==========================================

# Chỉ copy các file định nghĩa thư viện trước
COPY go.mod go.sum ./

# Chạy lệnh tải các dependency về container.
# Layer này cực kỳ nặng. Nhờ đặt ở đây, nó sẽ ĐƯỢC CACHE ở các lần build sau
# miễn là bạn không thêm/xóa thư viện nào trong go.mod/go.sum.
RUN go mod download

# ==========================================
# BƯỚC COPY SOURCE CODE VÀ BUILD ỨNG DỤNG
# ==========================================

# Copy toàn bộ mã nguồn còn lại vào container (Lệnh này thường xuyên làm mất cache)
COPY . .

# Biên dịch ứng dụng Golang thành file thực thi dạng nhị phân (binary)
# Vì lệnh COPY phía trên bị mất cache khi sửa code, nên lệnh RUN này cũng sẽ chạy lại.
# Tuy nhiên, lệnh build Go rất nhanh vì các dependency đã được tải sẵn ở layer trước.
RUN go build -o main .

# Lệnh chạy ứng dụng khi container khởi động (Tạo ra Container Layer)
CMD ["./main"]

```

---

### 4. Cạm bẫy cần tránh (Pitfalls)

* **Viết lệnh `COPY . .` quá sớm (Lỗi phổ biến nhất của người mới):**
Nếu bạn viết Dockerfile theo thứ tự:
```dockerfile
COPY . .
RUN go mod download

```


Hậu quả là: Mỗi lần bạn chỉ cần sửa một dòng log hoặc một dấu chấm trong file `.go`, Docker sẽ phát hiện layer `COPY . .` thay đổi $\rightarrow$ Hủy cache của lệnh này $\rightarrow$ Kéo theo lệnh `RUN go mod download` **phải chạy lại và tải lại toàn bộ thư viện từ internet**, làm chậm tiến độ công việc và lãng phí tài nguyên hệ thống một cách vô ích.
