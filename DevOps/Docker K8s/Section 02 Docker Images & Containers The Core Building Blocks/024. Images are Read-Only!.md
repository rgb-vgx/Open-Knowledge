# Docker Mastery: Lời Nguyền "Sửa Code Nhận Không Ăn" & Bản Chất Bất Biến Của Image

Bạn vừa đưa thành công service của mình lên container. Mọi thứ đang chạy mượt mà. Đột nhiên, bạn nhận ra API trả về sai một thông báo lỗi. Bạn mở IDE, sửa lại dòng text đó trong file mã nguồn, lưu lại (Save), và refresh trình duyệt... nhưng không có gì thay đổi.

Thông báo cũ vẫn trơ trơ ra đó, dù bạn thậm chí đã restart lại container. Chuyện quái gì đang xảy ra vậy?

Đây không phải là lỗi, đây là **tính năng cốt lõi** của kiến trúc Docker. Hôm nay, chúng ta sẽ mổ xẻ cơ chế đóng băng (snapshot) của Image và cách quản lý vòng đời code bên trong container.

---

## 1. Giải Phẫu Khái Niệm (Deep Dive): Image Là Một Khối Băng (Immutable Snapshot)

Hãy nhớ lại chỉ thị `COPY` trong `Dockerfile`:

```dockerfile
# Copy toàn bộ source code vào container
COPY . /app

```

Khi bạn chạy lệnh `docker build`, Docker Daemon sẽ thực thi tuần tự các bước. Đến bước `COPY`, nó sẽ chụp lại một bức ảnh (snapshot) toàn bộ trạng thái mã nguồn của bạn tại **ngay chính thời điểm đó**, rồi đóng gói vào một Layer của Image.

Từ giây phút lệnh build hoàn tất, **Image bị khóa lại (Locked/Read-only).** Nó hoàn toàn cắt đứt liên lạc với thư mục gốc trên máy tính của bạn.

* Nếu bạn sửa code ở máy host (bên ngoài) ➡️ Image không quan tâm.
* Nếu bạn xóa sạch thư mục code ở máy host ➡️ Image vẫn chạy bình thường.

Bản chất này được gọi là **Immutable Infrastructure** (Hạ tầng bất biến). Nó là chìa khóa để đảm bảo rằng một image khi chạy trên máy bạn, đẩy lên server staging, hay deploy ra production đều sẽ hoạt động chính xác 100% giống nhau, không bị ảnh hưởng bởi các thay đổi vô tình ở môi trường bên ngoài.

---

## 2. Thực Hành: Vòng Lặp "Sửa Code - Rebuild - Rerun"

Giả sử bạn đang viết một service bằng Go cho hệ thống KPI monitoring. Bạn có một file `main.go` trả về kết quả thành công, nhưng bạn muốn bổ sung thêm logic bắt lỗi "No response" tính là fail.

**Bước 1: Sửa code trên máy host**
Bạn cập nhật file `main.go`. Lúc này, file trên máy bạn đã mới, nhưng code bên trong container đang chạy (hoặc image đã build) vẫn là bản cũ.

**Bước 2: Dọn dẹp container cũ**
Tìm ID của container cũ và dừng nó lại (áp dụng trick gõ tắt ID):

```bash
docker ps
docker stop a3f  # Dừng container cũ
docker rm a3f    # Xóa luôn container cũ cho sạch sẽ

```

**Bước 3: Rebuild Image mới**
Để Docker "chụp" lại snapshot mới nhất của mã nguồn, bạn **bắt buộc** phải build lại. Lần này, hãy tập thói quen gắn tag phiên bản (versioning):

```bash
docker build -t kpi-backend:v2 .

```

*(Docker sẽ tạo ra một Image hoàn toàn mới, với một ID mới toanh. Code mới của bạn đã được `COPY` vào bản build này).*

**Bước 4: Chạy Container mới**
Giờ thì khởi động container từ Image vừa build:

```bash
docker run -d -p 8080:8080 --name kpi-service kpi-backend:v2

```

Bây giờ, khi gọi API, bạn sẽ thấy logic mới đã được áp dụng!

## 3. Best Practices & Cạm Bẫy (Pitfalls): Đừng Rebuild Trăm Lần Mỗi Ngày!

Nếu bạn đang nghĩ: *"Trời ơi, cứ mỗi lần gõ sai một dấu chấm phẩy lại phải chạy nguyên vòng lặp Stop -> Rebuild -> Run thì mất thời gian quá!"* — thì bạn hoàn toàn đúng.

Dưới góc nhìn của một System Engineer, chúng ta chia bài toán này thành 2 môi trường với 2 chiến lược đối lập:

* **Trên môi trường Production/Staging:** Tính bất biến (Immutability) là **vàng**. Bạn BẮT BUỘC phải build lại image mới mỗi khi có code mới, đẩy nó lên Registry (như Docker Hub/Harbor) và chạy lại. Điều này giúp dễ dàng rollback (lùi phiên bản) nếu code mới có bug.
* **Trên môi trường Development (Code ở Local):** Việc rebuild liên tục là một cực hình. Để giải quyết, chúng ta **không dùng lệnh `COPY` để test code local**. Thay vào đó, chúng ta sẽ sử dụng một cơ chế gọi là **Bind Mounts** (hoặc Volumes). Cơ chế này đục một "lỗ hổng không gian", map trực tiếp thư mục code trên máy thật (Kubuntu/Ubuntu của bạn) xuyên thẳng vào trong container. Bạn bấm Save code bên ngoài, ứng dụng bên trong container nhận được ngay lập tức (Hot Reload).

*(Cơ chế Volumes và Bind Mounts phức tạp này sẽ được mổ xẻ chi tiết ở bài học ngay sau đây).*

---

## 4. Tổng Kết

* **Quy tắc bất di bất dịch:** `docker build` tạo ra một snapshot. Mọi thay đổi code sau khi build xong sẽ **không** có tác dụng đối với image đó.
* **Muốn update code trên image:** Bạn phải chạy lại `docker build` để tạo ra một image mới (new ID), sau đó `docker run` lại image mới này.
* Sự cồng kềnh này là tính năng bảo vệ hệ thống trên Production (Immutable Infrastructure). Đối với môi trường dev, Docker có các công cụ (Volumes/Bind mounts) để bypass giới hạn này, giúp code tới đâu ăn tới đó.
