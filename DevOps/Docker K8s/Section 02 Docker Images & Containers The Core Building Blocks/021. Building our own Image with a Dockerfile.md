# Nghệ Thuật Viết Dockerfile: Đóng Gói Ứng Dụng Từ Zero Đến Hero

Ở bài trước, chúng ta đã chuẩn bị một mã nguồn (source code) hoàn toàn sạch sẽ, loại bỏ mọi sự phụ thuộc rườm rà trên máy local. Bây giờ là lúc chúng ta thực sự đóng gói nó thành một **Custom Image** bằng công cụ quyền năng nhất của Docker: **`Dockerfile`**.

File này chính là trái tim của mọi hệ thống CI/CD (Continuous Integration / Continuous Deployment). Nó là kịch bản tự động hóa kể cho Docker Engine biết từng bước, từng bước một phải làm thế nào để biến các file code thô sơ thành một môi trường chạy ứng dụng hoàn chỉnh.

---

## 1. Dockerfile Là Gì? Tại Sao Phải Là `Dockerfile`?

**`Dockerfile`** (viết hoa chữ D, không có phần mở rộng `.txt` hay `.sh`) là tên quy chuẩn mà Docker Engine sẽ tự động tìm kiếm khi bạn ra lệnh build. Nó chứa một chuỗi các **Instructions (Chỉ thị)**. Mỗi chỉ thị sẽ tạo ra một lớp (Layer) mới trong kiến trúc UnionFS mà chúng ta đã thảo luận.

> 💡 **Pro-Tip từ System Engineer:** Để có trải nghiệm viết code tốt nhất, hãy cài đặt extension **"Docker"** (phát triển bởi Microsoft) trong Visual Studio Code. Nó cung cấp tính năng auto-complete (tự động điền), tô màu cú pháp và cảnh báo lỗi (linting) cực kỳ hữu ích.

Hãy tạo file `Dockerfile` ngay tại thư mục gốc của dự án (cùng cấp với `server.js` và `package.json`).

---

## 2. Viết Dockerfile: Từng Dòng Lệnh Dưới Góc Nhìn Kiến Trúc Hệ Thống

Dưới đây là kịch bản đóng gói cho dự án Node.js của chúng ta. Tôi sẽ giải thích cặn kẽ ý nghĩa của từng chỉ thị.

### Chỉ thị 1: `FROM` - Xây Nền Móng
Lý thuyết của chúng ta là: Đừng bao giờ bắt đầu từ con số 0. Chúng ta cần một hệ điều hành đã được cài sẵn Node.js.

```

```text
File viet-dockerfile-chuan.md generated successfully.


```


dockerfile
FROM node:14

```
* **Ý nghĩa:** Docker sẽ lên Docker Hub tìm image `node:14` (hoặc lấy từ cache nội bộ nếu đã có). Toàn bộ OS, thư viện C++ và runtime của Node.js đã nằm sẵn ở đây. Mọi thứ chúng ta viết tiếp theo sẽ được "đắp" lên trên cái nền móng vững chắc này.

### Chỉ thị 2: `WORKDIR` - Thiết Lập Không Gian Làm Việc
Hệ thống file (File System) của Container hoàn toàn độc lập với máy Host. Theo mặc định, nếu bạn chạy lệnh, nó sẽ chạy ở thư mục gốc (Root `/`). Việc ném code ứng dụng bừa bãi vào thư mục gốc là tối kỵ về mặt bảo mật và quản lý.
```dockerfile
WORKDIR /app

```

* **Ý nghĩa:** Chuyển hướng con trỏ (tương tự lệnh `cd` trong Linux) vào thư mục `/app` bên trong Container. Nếu thư mục này chưa tồn tại, Docker sẽ tự động tạo ra nó. Từ giờ trở đi, mọi lệnh tiếp theo sẽ lấy `/app` làm bến đỗ.

### Chỉ thị 3: `COPY` - Bơm Máu Vào Trái Tim

Bây giờ, chúng ta cần đưa code từ máy tính cá nhân (Host) vào bên trong Container.

```dockerfile
COPY . /app

```

* **Ý nghĩa:** Cú pháp là `COPY <đường_dẫn_trên_Host> <đường_dẫn_trong_Container>`. Dấu `.` đầu tiên ám chỉ "toàn bộ thư mục hiện tại chứa file Dockerfile trên máy local". Chuỗi `/app` ám chỉ thư mục đích bên trong Container.
*(Lưu ý: Chúng ta có thể dùng `COPY . .` vì đã có `WORKDIR /app`, nhưng việc khai báo rõ `/app` như trên giúp code tường minh và dễ debug hơn rất nhiều).*

### Chỉ thị 4: `RUN` - Xây Dựng Các Tầng Tĩnh (Build Time)

Code đã vào container, nhưng nó chưa thể chạy vì thiếu các thư viện (dependencies) như `express`. Ta cần bảo Node.js tải chúng về.

```dockerfile
RUN npm install

```

* **Ý nghĩa:** Chỉ thị `RUN` sẽ thực thi lệnh hệ thống **TRONG QUÁ TRÌNH BUILD IMAGE**. Nó chạy lệnh `npm install` bên trong thư mục `/app`. Kết quả (thư mục `node_modules` vừa tải về) sẽ được "đóng băng" thành một layer tĩnh của Image.

### Chỉ thị 5: `EXPOSE` - Cắm Dây Mạng

Nhìn vào file `server.js`, ta thấy ứng dụng của mình đang khởi tạo một web server lắng nghe ở cổng `80`.
Nhưng như đã học, Container bị **Cô lập mạng (Network Isolated)** hoàn toàn.

```dockerfile
EXPOSE 80

```

* **Ý nghĩa:** Đây là một chỉ thị mang tính "tài liệu hóa" (documentation). Nó báo cho Docker Engine biết: *"Ê, thằng tiến trình bên trong container này sẽ mở cổng 80 đấy, lát nữa ai chạy container thì nhớ cấu hình map port nhé!"*. Mặc dù lệnh này không tự động mở port trên máy Host, nhưng nó là Best Practice bắt buộc phải có để các kỹ sư khác đọc file hiểu ngay hệ thống.

### Chỉ thị 6: `CMD` - Kích Hoạt Trái Tim (Run Time)

Cuối cùng, điều kiện để Container được sống là gì? Chính là phải có một Tiến trình chính (PID 1) chạy liên tục.

```dockerfile
CMD ["node", "server.js"]

```

* **Ý nghĩa:** Khác với `RUN` (chỉ chạy lúc build image), `CMD` là **LỆNH SẼ ĐƯỢC THỰC THI KHI CONTAINER BẮT ĐẦU CHẠY**.
* **Tại sao lại dùng mảng JSON `["node", "server.js"]`?** Đây là cú pháp *exec form*. Nó giúp truyền tín hiệu trực tiếp đến tiến trình Node mà không qua một lớp shell trung gian (như `/bin/sh -c`). Điều này cực kỳ quan trọng để hệ thống có thể bắt được các tín hiệu tắt an toàn (SIGTERM) khi bạn muốn dừng ứng dụng trên production.

## 3. Tổng Hợp File Hoàn Chỉnh

Gộp tất cả lại, file `Dockerfile` của bạn sẽ trông rõ ràng, mạch lạc như thế này:

```dockerfile
# 1. Chọn Base Image nền tảng
FROM node:14

# 2. Thiết lập thư mục làm việc nội bộ
WORKDIR /app

# 3. Copy toàn bộ mã nguồn vào container
COPY . /app

# 4. Cài đặt các thư viện phụ thuộc (Layer tĩnh)
RUN npm install

# 5. Khai báo port ứng dụng sử dụng
EXPOSE 80

# 6. Khởi chạy tiến trình chính khi Container bắt đầu
CMD ["node", "server.js"]

```

**Sự thật thú vị (Fun Fact) từ System Engineer:**
Liệu đây đã là một file Dockerfile hoàn hảo chưa? Sự thật là **CHƯA**. Cấu trúc này sẽ mắc phải cạm bẫy phá vỡ bộ đệm (Layer Caching Cache-busting) mà chúng ta đã nhắc đến ở bài mở đầu, khiến mỗi lần bạn sửa một dòng code nhỏ xíu, Docker lại phải tải lại toàn bộ thư viện `npm install` rất mất thời gian.

Tuy nhiên, với tư cách là bài học nhập môn, cấu trúc này hoàn toàn đủ để hệ thống hoạt động chính xác. Chúng ta sẽ "tối ưu hóa" nó (Optimization) trong các bài nâng cao về sau.

Bây giờ bạn đã có bản vẽ thiết kế (Dockerfile). Ở bước tiếp theo, hãy cùng mang bản vẽ này đến "nhà máy" Docker Engine để sản xuất ra một Custom Image thực thụ và khởi chạy nó!
