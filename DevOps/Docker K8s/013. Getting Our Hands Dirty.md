# "Hello World" Kiểu DevOps: Khởi Chạy Container Đầu Tiên Của Bạn

Nếu bạn là một kỹ sư backend đã quen với việc setup môi trường truyền thống (cài cắm Runtime, config biến môi trường, tải dependencies), thì bài viết hôm nay sẽ mang đến cho bạn một trải nghiệm mang tính "ma thuật".

Chúng ta sẽ khởi chạy một web server hoàn chỉnh mà **không hề cài đặt ngôn ngữ lập trình của nó lên máy chủ**. Đây chính là sức mạnh cốt lõi của Docker: "Zero-Install Environment" (Môi trường không cần cài đặt). Dù service của bạn được viết bằng Node.js, Go hay Python, quy trình đóng gói và vận hành sẽ hoàn toàn giống hệt nhau.

Hãy cùng xắn tay áo lên và bóc tách vòng đời của một Container từ lúc còn là mã nguồn cho đến khi trở thành một service đang chạy.

---

## 1. Mổ Xẻ Bài Toán: Tại Sao Phải Đóng Gói?

Hãy lấy một ví dụ thực tế: Chúng ta có một dummy backend service viết bằng **Node.js**. Đoạn code này sử dụng tính năng `top-level await` (gọi DB connection giả lập trước khi khởi động server).

Vấn đề kỹ thuật ở đây là: Cú pháp này **chỉ được hỗ trợ từ Node.js 14.3 trở lên**.

* **Cách làm truyền thống:** Bạn phải lên `nodejs.org`, tải đúng phiên bản 14.3+ về máy, chạy lệnh `npm install` để tải các thư viện bên thứ 3 (trong `package.json`), rồi mới gõ `node app.mjs` để chạy. Nếu máy bạn đang dùng Node 12 cho một dự án legacy khác, bạn sẽ gặp xung đột ngay lập tức.
* **Cách làm của DevOps/System Engineer:** Khoanh vùng dự án này lại. Chúng ta sẽ dùng Docker để tạo ra một không gian độc lập, nhét mã nguồn và đúng phiên bản Node.js cần thiết vào đó. Máy tính (Host OS) của bạn vẫn hoàn toàn sạch sẽ.

## 2. Giải Phẫu Dockerfile: Trái Tim Của Quá Trình Đóng Gói (Build)

Để Docker biết cách tạo ra môi trường đó, chúng ta cần một bản vẽ thiết kế. Bản vẽ này là một file text thuần túy có tên là `Dockerfile` (không có đuôi mở rộng).

Để hiểu sâu, bạn cần phân biệt hai khái niệm sinh tử trong Docker:

1. **Image (Ảnh tĩnh):** Là một gói (package) đóng băng (read-only) chứa toàn bộ OS layer, runtime (Node.js), thư viện và code của bạn. Nó giống như đĩa cài game ngày xưa.
2. **Container (Thực thể sống):** Là một process (tiến trình) đang chạy được khởi tạo từ Image đó. Nó giống như lúc bạn đang chơi game.

Dưới đây là `Dockerfile` chuẩn mực cho service Node.js của chúng ta:

```dockerfile
# 1. Base Image: Định nghĩa nền móng
# Chúng ta kéo một phiên bản Linux cực nhẹ đã cài sẵn Node.js
FROM node:14.17-alpine

# 2. Workdir: Định nghĩa thư mục làm việc bên trong Container
# Mọi lệnh RUN, COPY sau đó sẽ diễn ra trong thư mục này
WORKDIR /app

# 3. Copy file cấu hình thư viện trước (Best Practice để tối ưu Cache)
COPY package.json .

# 4. Cài đặt Dependencies bên trong Image
RUN npm install

# 5. Copy toàn bộ source code từ máy local vào Image
COPY . .

# 6. Expose: Khai báo cổng (Document purpose)
# Cổng 3000 là nơi app Node.js đang lắng nghe bên trong Container
EXPOSE 3000

# 7. CMD: Lệnh sẽ được thực thi khi Container KHỞI CHẠY (chứ không phải lúc Build Image)
CMD ["node", "app.mjs"]

```

## 3. Thực Hành: Build Image và Khởi Chạy Container

Mở Terminal của bạn tại thư mục chứa source code và `Dockerfile`. Đảm bảo Docker Engine (hoặc Docker Desktop) đang hoạt động.

### Bước 1: Build Image

Chúng ta sẽ "nung" cái `Dockerfile` kia thành một Image thực sự bằng lệnh:

```bash
docker build -t my-first-node-app .

```

* `docker build`: Lệnh ra chỉ thị tạo Image.
* `-t my-first-node-app`: (Tag) Đặt tên cho Image này để dễ nhớ. Nếu không có `-t`, Docker sẽ sinh ra một chuỗi ID vô nghĩa (như `7d9a1...`) rất khó quản lý.
* `.` (Dấu chấm): Chỉ định *Build Context*. Chữ này báo cho Docker biết: "Hãy tìm `Dockerfile` và source code ở ngay thư mục hiện tại".

Docker sẽ bắt đầu tải Base Image từ Docker Hub về, chạy lần lượt từng dòng lệnh và lưu lại thành một Image tĩnh.

### Bước 2: Run Container (Sự kỳ diệu của Port Binding)

Image đã có, giờ chúng ta khởi động nó thành một Container sống:

```bash
docker run -p 3000:3000 my-first-node-app

```

**Under the hood của cờ `-p` (Publish/Port Binding):**
Theo mặc định, Network của Container bị cách ly hoàn toàn với bên ngoài. Dòng `EXPOSE 3000` trong Dockerfile thực chất chỉ mang tính chất *tài liệu hóa*, nó không tự động đục tường lửa của container.
Để bạn (hoặc các service khác) có thể truy cập được API, bạn phải dùng `-p <Host_Port>:<Container_Port>`.

* `3000` (trái): Cổng trên máy tính thật của bạn (localhost).
* `3000` (phải): Cổng mà app đang chạy bên trong Container.

Khi bạn gõ lệnh này, Terminal sẽ bị "treo" (đứng im chờ log). Điều này chứng tỏ web server đang chạy ngầm trên port 3000. Hãy mở trình duyệt, truy cập `http://localhost:3000`, bạn sẽ thấy dòng chữ `"Hi there!"`.

**Bạn vừa chạy thành công một app Node.js mà máy bạn không hề có Node.js!**

### Bước 3: Quản Lý và Dọn Dẹp

Để xem các Container đang sống, hãy mở một Terminal mới và gõ:

```bash
docker ps

```

Bạn sẽ thấy Container của mình đang chạy cùng một Container ID (ví dụ: `a1b2c3d4...`) và cái tên được Docker đặt ngẫu nhiên (ví dụ: `quirky_einstein`).

Để tắt server một cách gọn gàng (Graceful shutdown), dùng lệnh:

```bash
docker stop <container_name_hoặc_container_id>

```

Lúc này, nếu reload lại trang localhost:3000, trang web sẽ báo lỗi vì Container đã chết.

## 4. Best Practices & Cạm Bẫy (Pitfalls) Cho Kỹ Sư Đàn Em

Dù đây chỉ là ví dụ vỡ lòng, có những "vết xe đổ" bạn cần tránh ngay từ ngày đầu tiên:

1. **Dùng ID thay vì Tag (Lỗi người mới):**
* Các tutorial cơ bản đôi khi bảo bạn build xong copy cái ID loằng ngoằng rồi chạy `docker run <ID>`. Trong thực tế CI/CD, không ai làm vậy. Luôn dùng cờ `-t` để đặt tên (`repo/app-name:version`) khi build.


2. **Thứ tự COPY sinh tử (Layer Caching):**
* Tại sao trong Dockerfile tôi lại tách `COPY package.json` rồi mới `RUN npm install`, sau đó mới `COPY . .` (copy toàn bộ code)?
* *Kiến trúc:* Docker build Image theo từng "Lớp" (Layer). Nếu một layer không đổi, Docker sẽ dùng lại cache để build siêu nhanh. Source code của bạn thay đổi liên tục, nhưng các thư viện (`package.json`) rất ít khi đổi. Nếu bạn gom chung lại `COPY . .` trước lệnh `RUN`, mỗi lần bạn sửa 1 dấu phẩy trong code, Docker sẽ phải hì hục tải lại (install) toàn bộ thư viện từ đầu rất tốn thời gian.


3. **Tập tin Rác lọt vào Image (`.dockerignore`):**
* Giống như Git, Docker có file `.dockerignore`. Luôn tạo file này và thêm thư mục như `node_modules`, `.git`, `.env` vào đó. Nó giúp ngăn chặn việc mang "rác" từ máy local vào trong Container, vừa làm Image bị phình to (tốn băng thông deploy), vừa tiềm ẩn rủi ro lộ lọt thông tin bảo mật (credentials).

## Tổng Kết

Chỉ với hai lệnh CLI cơ bản là `docker build` và `docker run`, bạn đã hoàn tất vòng đời cơ bản nhất của một ứng dụng Containerized. Đẹp đẽ nhất là sau toàn bộ quá trình thực hành này, máy tính (Host OS) của bạn vẫn nguyên vẹn — không có tàn dư của các bộ cài đặt, không rác thư viện.

Tuy nhiên, chạy một web server đứng trơ trọi chỉ là bước dạo đầu. Trong thực tế, service của bạn sẽ cần phải lưu trữ data, gọi ra các file cấu hình bên ngoài hoặc nói chuyện với một Database. Đó là lúc chúng ta phải giải bài toán về **Volumes** và **Networking** ở các phần tiếp theo.
