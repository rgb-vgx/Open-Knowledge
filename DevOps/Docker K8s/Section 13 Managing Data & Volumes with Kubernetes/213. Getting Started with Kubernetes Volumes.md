# Bắt đầu với Kubernetes Volumes: Các loại Volume phổ biến

## Tại sao cần Volumes trong Kubernetes?

Vấn đề bắt đầu khi containers bị restart. Ở demo app của chúng ta, chưa có cách nào rõ ràng để restart container — nhưng trong thực tế, có rất nhiều lý do khiến container crash: quá tải traffic, process timeout, lỗi code...

Khi container restart mà **không có volume**, tất cả dữ liệu bên trong container sẽ bị mất hoàn toàn.

## Các loại Volume trong Kubernetes

Kubernetes hỗ trợ **rất nhiều loại volume** — và danh sách này có thể trông khá choáng ngợp:

```yaml
volumes:
  - name: my-volume
    emptyDir: {}        # Loại đơn giản nhất
  - name: host-volume
    hostPath:           # Thư mục trên node machine
      path: /data
  - name: cloud-volume
    awsElasticBlockStore:  # AWS EBS
      volumeID: vol-xxx
  - name: nfs-volume
    nfs:                # Network File System
      server: nfs-server
      path: /exports
```

### Các loại chính cần quan tâm:

1. **`emptyDir`** — Thư mục trống, tạo mới mỗi khi pod start, xóa khi pod bị xóa
2. **`hostPath`** — Thư mục trên host machine (worker node)
3. **`CSI` (Container Storage Interface)** — Giao diện chung cho mọi loại storage bên thứ ba (AWS EFS, Azure Files, Ceph...)
4. **`awsElasticBlockStore`** — AWS EBS volume
5. **`nfs`** — Network File System

## Loại nào nên dùng?

Tùy vào môi trường:

- **Minikube/Local dev** → `emptyDir` hoặc `hostPath`
- **Production trên AWS** → `awsElasticBlockStore` hoặc CSI driver
- **Production trên Azure** → `azureDisk` hoặc CSI driver
- **Cần linh hoạt tối đa** → CSI (hỗ trợ mọi loại storage)

## Điểm chung của tất cả các loại

Dù bạn dùng loại nào, cách volume hoạt động bên trong container **luôn giống nhau** — đó chỉ là một đường dẫn (path) được mount vào container. Sự khác biệt duy nhất là **dữ liệu được lưu ở đâu bên ngoài container** tùy thuộc vào loại volume.

Trong section này, chúng ta sẽ tập trung vào 3 loại: `emptyDir`, `hostPath`, và `CSI`. Bắt đầu với `emptyDir` — loại đơn giản nhất.
