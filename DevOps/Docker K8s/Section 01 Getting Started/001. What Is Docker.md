# Docker Là Gì? Giải Phẫu Từ Khái Niệm Đến Cơ Chế Hoạt Động

Trong kiến trúc hệ thống hiện đại, đặc biệt là khi làm việc với Microservices hay CI/CD pipeline, có một "lời nguyền" luôn ám ảnh các lập trình viên: *"Code chạy ngon trên máy tôi, nhưng lên server thì lỗi!"*. Sự sai lệch về phiên bản OS, thiếu hụt thư viện hay xung đột môi trường là nguyên nhân chính. Và đó chính là bài toán mà **Docker** sinh ra để giải quyết.

Bài viết này sẽ bóc tách Docker từ những khái niệm bề mặt nhất cho đến cơ chế "under the hood", và hướng dẫn cách đóng gói một ứng dụng backend thực tế.

---

## Container Là Gì? "Chiếc Giỏ Picnic" Hiện Đại

Nếu bạn mới bắt đầu tìm hiểu, các tài liệu nhập môn thường ví Container như một **chiếc giỏ picnic**.

Hãy tưởng tượng bạn muốn đi dã ngoại. Thay vì đến nơi mới chạy đi mượn đĩa, tìm nĩa, mua đồ ăn (tương đương với việc lên server cài đặt môi trường, tải thư viện), bạn nhét *tất cả* thức ăn, dao kéo, đĩa chén vào một chiếc giỏ. Bạn xách chiếc giỏ đó ra công viên, lên núi hay ra biển, trải nghiệm ăn uống của bạn vẫn y hệt nhau.

Trong phần mềm, chiếc giỏ đó chính là **Container**. Nó là một đơn vị phần mềm được chuẩn hóa, đóng gói toàn bộ:

- **Mã nguồn ứng dụng** (Source code)
- **Runtime** (Ví dụ: Go runtime, Node.js, Python...)
- **Dependencies** (Các thư viện, module đi kèm)
- **System tools & Cấu hình môi trường**

Một ví von mang tính công nghiệp hơn chính là những chiếc **Container vận tải biển**. Trước đây, hàng hóa được bốc dỡ lộn xộn, đòi hỏi các loại tàu và xe khác nhau. Từ khi Container ra đời với kích thước tiêu chuẩn, mọi thứ được đóng vào thùng. Bất kể bên trong là gì, các cần cẩu, xe tải và tàu thủy đều dùng chung một chuẩn. Docker cũng vậy: nó tạo ra các container độc lập, tự vận hành và có thể chạy ở *bất cứ đâu* có cài đặt Docker Engine.

## Docker Hoạt Động Bằng Cách Nào? (Deep Dive Kiến Trúc)

Rất nhiều người nhầm tưởng Container là một dạng Máy ảo (Virtual Machine). **Hoàn toàn không phải.**

| Đặc điểm | Virtual Machine (VM) | Docker Container |
|---|---|---|
| Ảo hóa ở tầng | Phần cứng | Hệ điều hành |
| Guest OS | Cần Guest OS riêng (1-2GB RAM) | Share Host OS Kernel |
| Khởi động | Vài chục giây đến vài phút | Vài mili-giây |
| Kích thước | Hàng GB | Vài chục đến vài trăm MB |
| Hiệu năng | Bị hao hụt qua Hypervisor | Gần như native performance |

Docker thực chất là một lớp wrapper hoàn hảo thao tác với 2 tính năng cốt lõi của Linux Kernel:

**Namespaces** cung cấp sự cách ly (isolation). Khi chạy một container, Docker tạo ra một tập hợp các namespaces cho nó (PID để cách ly process, NET để cách ly network, MNT cho file system...). Nhờ đó, Process ID 1 trong container không hề biết đến sự tồn tại của các process ngoài máy host.

**Control Groups (cgroups)** cung cấp sự giới hạn (limitation). Giúp chia sẻ và giới hạn lượng tài nguyên phần cứng (CPU, Memory, Disk I/O) mà một container được phép dùng, tránh tình trạng một container bị lỗi phình to "ăn" hết RAM của hệ thống.

Docker Engine là một kiến trúc Client-Server gồm:

- **Docker Daemon** (`dockerd`): chạy ngầm quản lý mọi thứ
- **REST API**: cầu nối giao tiếp
- **Docker CLI**: nơi bạn gõ các lệnh `docker build`, `docker run`

## Thực Hành: Đóng Gói Backend Service Đạt Chuẩn

Giả sử chúng ta có một service viết bằng **Go (Golang)** cần kết nối với database **MongoDB**.

### Bước 1: Viết Dockerfile (Multi-stage Build)

Với ngôn ngữ biên dịch như Go, một lỗi phổ biến là bê nguyên môi trường build vào image chạy thật, khiến image nặng tới cả GB. Multi-stage Build là giải pháp:

```dockerfile
# ----- Stage 1: Build -----
FROM golang:1.21-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o backend-service ./main.go

# ----- Stage 2: Runtime -----
FROM alpine:latest
RUN apk --no-cache add ca-certificates
WORKDIR /root/
COPY --from=builder /app/backend-service .
EXPOSE 8080
CMD ["./backend-service"]
```

*Kết quả:* Image cuối cùng chỉ nặng khoảng 10-20MB thay vì gần 1GB.

### Bước 2: Dàn nhạc hóa với Docker Compose

```yaml
services:
  mongodb:
    image: mongo:latest
    container_name: dev_mongodb
    ports:
      - "27017:27017"
    volumes:
      - mongo_data:/data/db
    networks:
      - app_network

  api_service:
    build: .
    container_name: dev_golang_api
    ports:
      - "8080:8080"
    environment:
      - MONGO_URI=mongodb://mongodb:27017
    depends_on:
      - mongodb
    networks:
      - app_network

volumes:
  mongo_data:

networks:
  app_network:
    driver: bridge
```

> Ghi chú: Theo Docker Compose Specification hiện tại, trường top-level `version` chỉ còn mang tính tương thích ngược. Với Compose v2, bạn nên bỏ `version`.

Chỉ với một lệnh `docker-compose up -d`, cả database lẫn backend sẽ được dựng lên và tự động kết nối mạng.

## Best Practices Cho Môi Trường Production

### 1. Quản lý Dữ liệu (Volumes) & Tính Stateless

Container là "nhất thời" (ephemeral). Nếu container bị xóa, mọi dữ liệu lưu trực tiếp trong nó sẽ bốc hơi. App backend phải là Stateless. Những thứ cần lưu vĩnh viễn **bắt buộc** phải mount ra ngoài thông qua Volumes.

### 2. Tối ưu .dockerignore

Giống như `.gitignore`, file `.dockerignore` giúp loại bỏ thư mục như `.git`, IDE configs khỏi build context, tránh rò rỉ secret hoặc làm chậm build.

### 3. Đừng chạy với quyền Root

Mặc định, process trong container chạy dưới quyền root. Luôn tạo non-root user và sử dụng chỉ thị `USER`:

```dockerfile
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
```

### 4. Graceful Shutdown

Khi scale down hoặc cập nhật phiên bản, Docker gửi tín hiệu `SIGTERM`. Đảm bảo code xử lý chuẩn tín hiệu ngắt của OS để đóng connection từ từ.

## Tóm Tắt

Khái niệm "giỏ picnic" hay "container vận tải" giúp dễ hình dung Docker, nhưng giá trị cốt lõi nằm ở khả năng **đóng gói chuẩn hóa**, **cách ly môi trường** và **khả năng tái tạo**.

Nắm vững tối ưu `Dockerfile` và quản lý stack bằng `docker-compose` không chỉ giúp môi trường local sạch sẽ hơn, mà còn là bước đệm bắt buộc nếu muốn tiến xa hơn vào CI/CD tự động và Kubernetes.
