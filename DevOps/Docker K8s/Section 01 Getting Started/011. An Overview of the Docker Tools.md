# Kiến Trúc Docker Engine & Hệ Sinh Thái: Mổ Xẻ "Trái Tim" Của Docker

Sau khi cài đặt thành công Docker, với tư cách là Backend Engineer, bạn không thể nhắm mắt gõ lệnh mà không hiểu hệ thống bên dưới đang xử lý ra sao. Lệnh bạn gõ đi về đâu? Ai là người thực thi? Bài viết này sẽ giải phẫu kiến trúc Docker Engine và giới thiệu những "mảnh ghép" quan trọng nhất trong hệ sinh thái.

---

## Docker Engine: Không Chỉ Là Một Cục Code

Khi nghe ai đó nói "Cài Docker đi", thực chất là cài **Docker Engine**. Theo tài liệu kiến trúc từ Docker.com, Docker Engine không phải ứng dụng đơn lẻ, mà là hệ thống Client-Server gồm 3 thành phần cốt lõi:

1. **Docker Daemon (`dockerd`):** "Trái tim" và bộ não của Docker. Là tiến trình chạy ngầm trên hệ điều hành, lắng nghe yêu cầu và thực hiện các công việc nặng nhọc: tạo, chạy, quản lý Containers, Images, Networks và Volumes.

2. **REST API:** Cầu nối giao tiếp. `dockerd` mở ra API (thông qua UNIX socket `unix:///var/run/docker.sock` trên Linux hoặc giao diện mạng TCP). Mọi công cụ muốn điều khiển Docker đều phải gọi qua API này.

3. **Docker CLI (`docker` command):** "Điều khiển từ xa". Khi bạn gõ `docker run...`, CLI dịch lệnh thành HTTP REST request gửi tới Docker Daemon. Daemon xử lý xong trả kết quả về cho CLI hiển thị lên màn hình.

> **Sự thật phũ phàng:** CLI và Daemon có thể nằm ở hai máy tính hoàn toàn khác nhau. Bạn có thể dùng Docker CLI trên laptop Mac để điều khiển Docker Daemon chạy trên server Ubuntu ở trung tâm dữ liệu, miễn là cấu hình API bảo mật đúng cách.

## Hệ Sinh Thái Docker: Những Vũ Khí Đi Kèm

Docker Engine chỉ là nền tảng cốt lõi. Để triển khai backend thực tế, chúng ta cần thêm các công cụ trong hệ sinh thái:

### Docker Hub (Registry)

Nếu GitHub là nơi lưu trữ mã nguồn, thì Docker Hub là nơi lưu trữ các Docker Image. Đây là kho lưu trữ đám mây khổng lồ. Khi bạn gõ `docker pull nginx`, Docker tự động kết nối Docker Hub và tải image về máy.

### Docker Compose

Quản lý một container thì dễ, nhưng hệ thống cần 5 containers chạy cùng lúc thì sao? Docker Compose định nghĩa toàn bộ cụm dịch vụ chỉ bằng file `docker-compose.yml`. Thay vì gõ 5 lệnh CLI dài ngoằng, chỉ cần một lệnh duy nhất để dàn nhạc khởi chạy.

### Kubernetes (K8s)

Nếu Docker Compose dùng trên môi trường *Development*, thì Kubernetes là "trùm cuối" dàn nhạc trên môi trường *Production*. Khi có hàng trăm containers cần tự động scale, tự động phục hồi khi chết và load balancing, Docker Engine đơn thuần không đủ sức. Kubernetes đứng ở tầng trên, ra lệnh cho hàng loạt Docker Engine ở nhiều server.

### OCI Compliance Stack

Docker Engine hiện đại tuân thủ chuẩn **OCI (Open Container Initiative)**:

- **OCI Image Spec:** Định dạng image layer, manifest, config
- **OCI Runtime Spec:** Tiêu chuẩn runtime (runc, crun, kata-containers)
- **OCI Distribution Spec:** Giao thức registry (Docker Hub, Harbor, ECR)

| Component | OCI Spec | Mô tả |
|---|---|---|
| `runc` | Runtime Spec | Runtime mặc định, tạo namespaces/cgroups |
| `containerd` | — | Daemon quản lý lifecycle image/container |
| `dockerd` | Image/Distribution | API server + builder + registry client |

## Thực Hành: Chứng Minh Kiến Trúc Client-Server

Mở Terminal và gõ:

```bash
docker version
```

Kết quả chia làm hai phần rõ rệt:

```yaml
Client: Docker Engine - Community
 Version:           24.0.5
 API version:       1.43
 Go version:        go1.20.6
 OS/Arch:           linux/amd64

Server: Docker Engine - Community
 Engine:
  Version:          24.0.5
  API version:      1.43 (minimum version 1.12)
  containerd:
   Version:          1.6.22
```

Nếu Docker Daemon bị tắt (quên bật Docker Desktop), phần **Server** sẽ báo lỗi. CLI vẫn chạy bình thường nhưng không tìm thấy não bộ để xử lý lệnh.

Tiếp theo, thử chạy container đầu tiên:

```bash
docker run hello-world
```

**Điều gì xảy ra under the hood?**

1. Docker Client gửi yêu cầu `run hello-world` tới Docker Daemon
2. Daemon kiểm tra image `hello-world` đã có trên máy chưa
3. Nếu chưa, Daemon kết nối ra Internet, truy cập **Docker Hub** và tải image về
4. Daemon khởi tạo môi trường cách ly (Container) từ image và chạy mã nguồn bên trong
5. Mã source in ra dòng chữ chào mừng, Daemon gửi ngược lại cho CLI

## Best Practices & Cạm Bẫy

### 1. Lỗi Permission Denied với Docker Socket

Giao tiếp giữa Client và Daemon đi qua file `/var/run/docker.sock`. Mặc định chỉ có user `root` mới có quyền đọc/ghi. **Tuyệt đối không lạm dụng `sudo docker...`**. Hãy đưa user vào group `docker` như đã hướng dẫn ở bài trước.

### 2. Docker Hub Rate Limiting

Trên môi trường CI/CD, nếu pipeline liên tục pull image từ Docker Hub ẩn danh (không login), bạn sẽ nhanh chóng chạm giới hạn (khoảng 100 lần pull / 6 giờ / IP). Pipeline sẽ tạch hàng loạt.

**Best Practice:** Luôn dùng tài khoản Docker Hub để đăng nhập (`docker login`) trên server build, hoặc thiết lập Registry Cache nội bộ.

### 3. Hiểu lầm về Docker Compose

Compose **không phải** công cụ thay thế Docker Engine. Nó chỉ là công cụ "đọc" file YAML và tự động gọi các lệnh CLI giùm bạn. Trái tim thực sự chạy app vẫn là Docker Daemon.

## Tóm Tắt

Bạn đã đi từ việc hiểu cơ sở lý thuyết ảo hóa, lựa chọn giải pháp cài đặt, cho đến nhìn thấu kiến trúc Client-Server ẩn sau những dòng lệnh CLI. Bạn cũng đã nắm được vai trò của Docker Hub, Docker Compose và mục tiêu cuối cùng là Kubernetes.

Bộ não (Daemon) đã sẵn sàng, chiếc điều khiển (CLI) đã nằm trong tay. Trong bài tiếp theo, chúng ta sẽ "xắn tay áo" lên, sử dụng CLI để nhào nặn các Image và quản lý vòng đời Container một cách chuyên nghiệp nhất.
