# Docker Images & Containers: Giải Mã "DNA" Của Thế Giới Containerization

Giả định rằng bạn đã cài đặt Docker Engine thành công trên môi trường Linux (Ubuntu/Kubuntu) của mình. Giờ là lúc chúng ta xắn tay áo lên và đối mặt với hai khái niệm nền tảng, mang tính sống còn mà bất kỳ kỹ sư hệ thống nào cũng phải nằm lòng: **Images** và **Containers**.

Nếu không hiểu rõ mối quan hệ mật thiết giữa hai thành tố này, bạn sẽ rất dễ rơi vào ma trận lỗi khi cấu hình hệ thống thực tế.

---

## 1. Giải Phẫu Khái Niệm: Image và Container Thực Chất Là Gì?

Cách dễ nhất đối với một lập trình viên Backend để hiểu hai khái niệm này là đối chiếu chúng với mô hình Lập trình hướng đối tượng (OOP).

### Docker Image (Khuôn mẫu - The Class)

Theo định nghĩa chuẩn: *"An image is a read-only template with instructions for creating a Docker container."* (Image là một bản mẫu chỉ đọc, chứa các chỉ dẫn để tạo ra một Docker container).

* **Bản chất:** Image chính là "DNA" của ứng dụng. Nó là một gói tĩnh (static package) chứa mọi thứ hệ thống cần để chạy: hệ điều hành base (ví dụ: Alpine, Ubuntu), mã nguồn ứng dụng (ví dụ: file binary Go), các thư viện phụ thuộc (dependencies), các biến môi trường và cấu hình hệ thống.
* **Đặc tính:** Nó **Read-only (Chỉ đọc)**. Khi một Image đã được build xong, bạn không thể thay đổi nội dung bên trong nó. Nếu muốn sửa code, bạn buộc phải build lại một Image mới.
* **Cơ chế hoạt động:** Image được cấu tạo từ nhiều **Layers (Tầng)** xếp chồng lên nhau thông qua UnionFS (Union File System). Mỗi dòng lệnh trong `Dockerfile` (như `RUN`, `COPY`, `ADD`) sẽ tạo ra một layer mới.

### Docker Container (Thực thể - The Object/Instance)

* **Bản chất:** Container là một phiên bản "đang chạy" (runnable instance) của một Image. Nếu Image là bản vẽ thiết kế của chiếc xe, thì Container chính là chiếc xe đang lăn bánh trên đường.
* **Đặc tính:** Khi bạn khởi chạy một Container từ một Image, Docker Engine sẽ "đắp" thêm một **Read-Write Layer (Tầng có thể Đọc-Ghi)** mỏng lên trên cùng các tầng Read-only của Image gốc.
* **Mối quan hệ:** Từ **MỘT** Docker Image duy nhất, bạn có thể khởi chạy **HÀNG TRĂM** Docker Containers hoàn toàn độc lập với nhau. Mỗi container sẽ có không gian bộ nhớ, Network (IP riêng) và cây tiến trình phân lập nhờ cơ chế Linux Namespaces.

## 2. Thực Chiến: Vòng Đời Của Image & Container

Hệ sinh thái Docker xoay quanh hai loại Images: **Pre-built Images** (đã được cộng đồng hoặc các tổ chức build sẵn trên Docker Hub) và **Custom Images** (do chính tay chúng ta tự viết `Dockerfile` để build).

Hãy bật Terminal lên và đi qua các luồng thao tác thực tế.

### Thao tác 1: Sử dụng Pre-built Image và Khởi chạy Container

Giả sử bạn cần một môi trường Redis để test cache cho hệ thống. Thay vì phải `apt-get install redis-server` và config loằng ngoằng, bạn chỉ cần dùng pre-built image.

```bash
# 1. Tải image từ Docker Hub (Registry) về máy local
docker pull redis:7.0-alpine

# 2. Kiểm tra danh sách images đang có trên máy
docker images 
# Hoặc: docker image ls

# 3. Khởi chạy một Container từ Image vừa tải
# Cờ -d (detach): Chạy ngầm
# Cờ --name: Đặt tên cho container để dễ quản lý
# Cờ -p 6379:6379: Map port của máy Host với port của Container
docker run -d --name local_redis_cache -p 6379:6379 redis:7.0-alpine

```

Lúc này, một instance của Redis đang chạy hoàn hảo trên máy bạn. Hoàn toàn sạch sẽ, không can thiệp vào các service hệ thống của Ubuntu.

### Thao tác 2: Build Custom Image cho Ứng dụng Backend

Tương tự như ví dụ về ứng dụng Go API ở bài trước. Từ file mã nguồn và `Dockerfile`, ta sẽ tạo ra một Custom Image.

```bash
# Đứng tại thư mục chứa Dockerfile và code
# Lệnh build image. Cờ -t để gắn tên (tag) cho image. 
# Dấu "." ám chỉ context build là thư mục hiện tại.
docker build -t my-go-api:v1.0 .

# Chạy một container từ custom image vừa build
docker run -d --name backend_service_1 -p 8080:8080 my-go-api:v1.0

```

### Thao tác 3: Quản lý vòng đời Container

Đây là các lệnh "cơm bữa" bạn sẽ dùng để quản trị hệ thống:

```bash
# Xem các containers ĐANG CHẠY
docker ps

# Xem TẤT CẢ các containers (kể cả đã bị stop)
docker ps -a

# Dừng một container đang chạy (Gửi tín hiệu SIGTERM để ứng dụng shutdown an toàn)
docker stop backend_service_1

# Khởi động lại container đã dừng
docker start backend_service_1

# Xóa vĩnh viễn một container (Chỉ xóa được khi container đã stop)
docker rm backend_service_1

```

## 3. Best Practices & Cạm Bẫy (Pitfalls) Trên Môi Trường Thực Tế

Là một kỹ sư đàn anh, tôi khuyên bạn nên khắc cốt ghi tâm những điều sau khi làm việc với Images và Containers:

### ⚠️ Cạm bẫy 1: Hội chứng "Rác thải Docker" (Dangling Images & Stopped Containers)

Mỗi lần bạn gõ `docker build`, nếu code có thay đổi, Docker tạo ra các layer mới. Các image cũ mất đi tag tên và trở thành các hình bóng mồ côi (dangling images - hiển thị là `<none>`). Cùng với đó là hàng tá các container đã bị stop nhưng chưa bị `rm`. Chúng âm thầm "ăn" hàng chục, thậm chí hàng trăm GB ổ cứng của bạn.
**👉 Best Practice:** Định kỳ chạy lệnh dọn dẹp hệ thống. Nó sẽ dọn sạch các container đã stop, dangling images và networks không dùng đến.

```bash
docker system prune -f

```

### ⚠️ Cạm bẫy 2: Lạm dụng Tag `:latest`

Khi gõ lệnh `docker pull ubuntu`, mặc định Docker sẽ lấy tag `ubuntu:latest`. Trên môi trường Development thì không sao, nhưng đem lên Production là một thảm họa. Hôm nay `:latest` là bản 20.04, ngày mai nó tự cập nhật thành 22.04 với các thư viện bị thay đổi hoàn toàn, làm ứng dụng của bạn crash một cách bí ẩn.
**👉 Best Practice:** Luôn luôn (always!) chỉ định đích danh version (Specific Tag) khi khai báo Image. Ví dụ: `golang:1.21-alpine` thay vì `golang:alpine`.

### ⚠️ Cạm bẫy 3: Hiểu nhầm về tính bền vững (Persistence)

Như đã nhắc ở phần khái niệm, layer Read-Write của container gắn liền với vòng đời của container đó. Nếu bạn gõ lệnh `docker rm`, toàn bộ dữ liệu sinh ra trong quá trình container chạy (file log, dữ liệu database) sẽ **biến mất vĩnh viễn**.
**👉 Best Practice:** Container sinh ra để xử lý tác vụ (Compute), không phải để lưu trữ (Storage). Để lưu trữ dữ liệu bền vững, chúng ta bắt buộc phải sử dụng **Volumes** — và đây chính là chủ đề hấp dẫn chúng ta sẽ mổ xẻ ở bài học tiếp theo!
