# Kiến Trúc Docker Engine & Bức Tranh Toàn Cảnh: Mổ Xẻ "Trái Tim" Của Hệ Sinh Thái

Ở các bài viết trước, chúng ta đã cài đặt thành công Docker lên máy tính. Dù bạn dùng Linux thuần, Docker Desktop cho Mac/Windows hay thậm chí là giải pháp "cổ đại" Docker Toolbox, thì đích đến cuối cùng của chúng ta đều chung một thứ: **Đưa Docker Engine vào hoạt động.**

Nhưng với tư cách là một Backend Engineer, bạn không thể nhắm mắt gõ lệnh mà không hiểu hệ thống bên dưới đang xử lý ra sao. Lệnh bạn gõ đi về đâu? Ai là người thực thi nó? Bài viết này sẽ giải phẫu kiến trúc của Docker Engine và giới thiệu nhanh những "mảnh ghép" quan trọng nhất trong hệ sinh thái (Docker Hub, Compose, Kubernetes) mà bạn sẽ sử dụng hàng ngày.

---

## 1. Giải Phẫu Khái Niệm: Docker Engine Không Chỉ Là Một Cục Code

Khi bạn nghe ai đó nói "Cài Docker đi", thực chất là họ đang nói đến việc cài đặt **Docker Engine**. Theo tài liệu kiến trúc chuẩn từ Docker.com, Docker Engine không phải là một ứng dụng đơn lẻ, mà là một hệ thống Client-Server (Khách - Chủ) bao gồm 3 thành phần cốt lõi:

1. **Docker Daemon (`dockerd` - Thành phần Server):** Đây chính là "trái tim" và bộ não của Docker. Nó là một tiến trình (process) chạy ngầm liên tục trên hệ điều hành (trên Linux hoặc trong máy ảo WSL2/Hyper-V). Nhiệm vụ của nó là lắng nghe các yêu cầu và trực tiếp thực hiện các công việc nặng nhọc: tạo, chạy, quản lý Containers, Images, Networks và Volumes.
2. **REST API:** Đây là cầu nối giao tiếp. `dockerd` không trực tiếp nói chuyện với con người; nó mở ra một API (thường thông qua một UNIX socket `unix:///var/run/docker.sock` trên Linux hoặc giao diện mạng TCP). Mọi công cụ muốn điều khiển Docker đều phải gọi qua API này.
3. **Docker CLI (`docker` command - Thành phần Client):** Đây là chiếc "điều khiển từ xa". Khi bạn mở Terminal và gõ `docker run...`, giao diện dòng lệnh (CLI) này sẽ dịch lệnh của bạn thành một HTTP REST request và gửi tới Docker Daemon. Daemon xử lý xong sẽ trả kết quả về cho CLI hiển thị lên màn hình của bạn.

> **Sự thật phũ phàng:** Chiếc "điều khiển" (CLI) và "trái tim" (Daemon) có thể nằm ở hai máy tính hoàn toàn khác nhau. Bạn hoàn toàn có thể dùng Docker CLI trên laptop Mac của mình để điều khiển một Docker Daemon đang chạy trên một server Ubuntu ở Viettel Data Center, miễn là bạn cấu hình API bảo mật đúng cách.

## 2. Hệ Sinh Thái Docker: Những Vũ Khí Đi Kèm

Docker Engine chỉ là nền tảng cốt lõi. Để triển khai một hệ thống backend thực tế (như một cụm microservices viết bằng Go, Redis caching, và MongoDB), chúng ta cần thêm các công cụ hỗ trợ trong hệ sinh thái:

* **Docker Hub (Registry):** Nếu GitHub là nơi lưu trữ mã nguồn (Source code), thì Docker Hub là nơi lưu trữ các bản build đóng gói (Docker Images). Đây là một kho lưu trữ đám mây khổng lồ. Khi bạn cần một database, bạn không cần tự build từ đầu, chỉ cần bảo Docker Daemon kéo (pull) image chính thức của PostgreSQL từ Docker Hub về chạy. Bạn cũng sẽ dùng nó (hoặc các Private Registry tương tự) để chia sẻ image của chính team mình.
* **Docker Compose:** Quản lý một container thì dễ, nhưng hệ thống backend của bạn cần 5 containers chạy cùng lúc và nói chuyện với nhau thì sao? Docker Compose là một công cụ (bọc ngoài Docker Engine) cho phép bạn định nghĩa toàn bộ cụm dịch vụ đó chỉ bằng một file `docker-compose.yml`. Thay vì gõ 5 lệnh CLI dài ngoằng, bạn chỉ cần một lệnh duy nhất để dàn nhạc khởi chạy.
* **Kubernetes (K8s):** Nếu Docker Compose dùng để dàn nhạc trên môi trường *Development* (máy local), thì Kubernetes là "trùm cuối" dàn nhạc trên môi trường *Production*. Khi bạn có hàng trăm containers cần tự động scale (mở rộng), tự động phục hồi khi chết (auto-healing) và load balancing, Docker Engine đơn thuần là không đủ sức. Kubernetes sẽ đứng ở tầng trên, ra lệnh cho hàng loạt Docker Engine ở nhiều server khác nhau. (Chúng ta sẽ có một phần riêng biệt cực sâu về K8s ở cuối series).

## 3. Thực Hành: Chứng Minh Kiến Trúc Client-Server Bằng CLI

Để thấy rõ sự tách biệt giữa Client và Server (Daemon) mà chúng ta vừa học, hãy mở Terminal/PowerShell lên và gõ lệnh sau:

```bash
docker version
```

Hãy nhìn kỹ vào kết quả trả về, bạn sẽ thấy nó chia làm hai phần rõ rệt (Client và Server):

```yaml
Client: Docker Engine - Community
 Version:           24.0.5
 API version:       1.43
 Go version:        go1.20.6
 OS/Arch:           linux/amd64

Server: Docker Engine - Community
 Engine:
  Version:          24.0.5
  API version:      1.43 (minimum version 1.12)
  Go version:       go1.20.6
  OS/Arch:          linux/amd64
 containerd:
  Version:          1.6.22
```

Nếu Docker Daemon của bạn bị tắt (ví dụ bạn quên bật Docker Desktop), phần **Server** sẽ báo lỗi không thể kết nối. CLI (Client) vẫn chạy bình thường, nhưng nó không tìm thấy não bộ để xử lý lệnh.

Tiếp theo, hãy thử chạy container đầu tiên để test toàn bộ luồng hoạt động: (CLI -> API -> Daemon -> Docker Hub -> Container)

```bash
docker run hello-world
```

**Điều gì thực sự xảy ra under the hood?**

1. Docker Client gửi yêu cầu `run hello-world` tới Docker Daemon.
2. Daemon kiểm tra xem image `hello-world` đã có trên máy tính của bạn chưa.
3. Nếu chưa, Daemon tự động kết nối ra ngoài Internet, truy cập vào **Docker Hub** và tải (pull) image đó về máy.
4. Sau khi tải xong, Daemon khởi tạo một môi trường cách ly (Container) từ image đó và chạy mã nguồn bên trong.
5. Mã nguồn in ra dòng chữ chào mừng, Daemon thu thập kết quả đó và gửi ngược lại cho Client in ra Terminal của bạn.

## 4. Best Practices & Cạm Bẫy (Pitfalls) Cần Tránh

1. **Lỗi Permission Denied với Docker Socket (Rất hay gặp trên Linux):**
* *Nguyên nhân:* Giao tiếp giữa Client và Daemon đi qua file `/var/run/docker.sock`. Mặc định chỉ có user `root` mới có quyền đọc/ghi file này.
* *Khắc phục:* Tuyệt đối không lạm dụng `sudo docker...`. Hãy cấu hình cấp quyền cho user của bạn như đã hướng dẫn ở bài trước (đưa user vào group `docker`).
2. **Docker Hub Rate Limiting (Giới hạn lượt tải):**
* *Cạm bẫy:* Trên môi trường CI/CD (như GitLab CI, Jenkins), nếu các pipeline của bạn liên tục kéo image (ví dụ: `node:alpine` hay `golang:alpine`) từ Docker Hub ẩn danh (không login), bạn sẽ rất nhanh chóng chạm giới hạn (Rate limit) của Docker Hub (khoảng 100 lần kéo / 6 giờ / IP). Pipeline của team bạn sẽ tạch hàng loạt.
* *Best Practice:* Luôn luôn dùng tài khoản Docker Hub để đăng nhập (`docker login`) trên các server build, hoặc thiết lập một Registry Cache nội bộ trong công ty để giảm tải việc gọi ra ngoài internet.
3. **Hiểu lầm về Docker Compose:**
* Compose không phải là công cụ thay thế Docker Engine. Nó chỉ là một công cụ "đọc" file YAML và tự động gọi các lệnh CLI giùm bạn. Trái tim thực sự chạy app vẫn là Docker Daemon.
