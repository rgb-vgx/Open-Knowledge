# Partition Không Phải Là File: Hiểu Segments Và Indexes Để Không Sập Vì too many open files

Bạn tưởng một partition là một file log khổng lồ ghi mãi không hết? Thực tế broker chẻ mỗi partition thành hàng loạt **segments** nhỏ 1GB, mỗi segment kèm 2 index. Không hiểu tầng này thì không thể hiểu retention, compaction, và sẽ ngơ ngác khi broker báo `too many open files`. Bài này xuống tận đĩa cứng.

---

## 1. Cơ Chế: Partition → Segments → Chỉ Một Active Segment Được Ghi

```
Partition 0
├── Segment 0   offsets 0 – 957        (closed)
├── Segment 1   offsets 958 – 1675     (closed)
└── Segment 2   offsets 1676 – ...     (ACTIVE, đang ghi tuần tự)
```

- Mỗi segment là một dải offsets liên tục. Segment cũ đóng lại (closed), chỉ **active segment** mới nhất được append tuần tự.
- Tại một thời điểm, mỗi partition chỉ có **đúng một active segment**. Writes luôn nối đuôi active segment, không ghi lung tung.
- Mở thư mục data của Kafka (`log.dirs`) bạn sẽ thấy các file `.log`, `.index`, `.timeindex` — đó chính là segments.

## 2. Config: Hai Nút Vặn Đóng/Mở Segment

| Config | Default | Ý nghĩa |
|---|---|---|
| `log.segment.bytes` | 1 GB (`1073741824`) | Segment đạt kích thước này → đóng lại, mở segment mới |
| `log.segment.ms` | 1 tuần | Quá thời gian này dù chưa đầy 1GB → vẫn đóng, mở segment mới |

Kafka tạo segment mới khi **một trong hai** điều kiện chạm ngưỡng. Hai index đi kèm mỗi segment:

- **offset → position index** (`.index`): tìm offset số N nằm ở byte nào để đọc nhanh, không scan cả file.
- **timestamp → offset index** (`.timeindex`): tìm message theo timestamp (phục vụ `offsetsForTimes`, replay theo giờ).

Chính cặp index này làm Kafka đọc được message bất kỳ trong hàng TB log gần như O(1).

## 3. Lệnh Demo: Nhìn Segments Bằng Mắt Thường

```bash
# Tìm thư mục data trong server.properties
grep log.dirs config/kraft/server.properties

# Liệt kê segments của một partition
ls -lh /tmp/kraft-combined-logs/my-topic-0/
# 00000000000000000000.log  00000000000000000000.index  00000000000000000000.timeindex
# 00000000000000000958.log  ...
```

Tên file chính là **base offset** của segment đó.

## 4. Trade-offs: Segment Nhỏ Thì Compaction Nhanh Nhưng File Nổ Tung

| Lựa chọn | Được gì | Mất gì |
|---|---|---|
| `log.segment.bytes` nhỏ (ví dụ 100MB) | Nhiều segments → retention và **log compaction trigger thường xuyên hơn** (chi tiết 3 bài sau) | Broker phải mở giữ hàng nghìn files → tốn file handles, RAM, dễ dính `too many open files` |
| `log.segment.ms` nhỏ (ví dụ 1 ngày thay vì 7 ngày) | Compaction/cleanup tối đa mỗi ngày một lần thay vì mỗi tuần | Cleanup chạy thường xuyên tốn CPU/RAM của log cleaner |
| Giữ default 1GB/7 ngày | Ổn định, ít file | Topic throughput thấp thì cả tuần chưa đủ 1 segment → compaction gần như không chạy |

Quy tắc chọn: throughput cao thì **đừng đụng** default. Throughput thấp mà cần compaction nhanh thì mới hạ 2 ngưỡng này xuống — và phải nâng `ulimit -n` của broker tương ứng.

## Pitfalls / Best Practice Production

- **Pitfall: hạ `log.segment.bytes` quá tay "cho compaction nhanh" rồi broker crash vì hết file descriptor.** Mỗi segment = 3 files × số partitions × replication — nhân lên rất nhanh.
- **Pitfall: tưởng setting segment là per-topic duy nhất.** Nó có cả bản broker-level (`log.segment.bytes`) và topic-level override — check thứ tự ưu tiên trước khi sửa.
- **Best practice:** người mới **không sửa 2 setting này**. Hiểu nó để đọc tiếp log cleanup policy, khi nào compaction chậm mới quay lại tune.

## Kết Luận

Tóm lại: **partition là dãy segments nối đuôi nhau, chỉ active segment được ghi, mỗi segment kèm offset index và timestamp index; segment càng nhỏ thì cleanup/compaction càng mau nhưng broker càng nặng.**

Có nền file rồi, giờ lên tầng chính sách: dữ liệu hết hạn thì xóa kiểu gì? Bài tiếp theo tổng quan **2 log cleanup policies: delete vs compact**.
