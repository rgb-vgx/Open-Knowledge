# Đừng Để Default Broker Quyết Định Số Phận Topic: Đổi Config Đúng Cách Với kafka-configs.sh

Broker Kafka đi kèm default cho mọi topic config: replication, partitions, message size, `log.cleanup.policy`, `min.insync.replicas`... Dùng mãi default thì topic thanh toán quan trọng ngang topic log rác — đến lúc mất data mới biết. Bài này học cách override config theo từng topic mà không cần restart broker.

---

## 1. Cơ Chế: Default Của Broker Chỉ Là Điểm Rơi

Mỗi topic sinh ra sẽ thừa hưởng config default từ broker. Nhưng từng topic có yêu cầu khác nhau: topic tiền cần `replication.factor` cao và `min.insync.replicas=2`, topic tracking click có thể chịu mất mát để lấy throughput. Vì vậy Kafka cho phép **dynamic topic config** đè lên default, xem được bằng lệnh describe.

Danh sách đầy đủ topic configs nằm trong tài liệu Apache Kafka (topic-level configs). Bài này demo với `min.insync.replicas`.

## 2. Config Và Lệnh Demo: Tạo → Xem → Sửa → Xóa

Giữ nguyên lệnh demo trong transcript, chỉ tách dòng cho dễ đọc:

**Bước 1 — tạo topic test:**

```bash
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic configured-topic \
  --replication-factor 1 --partitions 3
```

**Bước 2 — kiểm tra config hiện tại (đang rỗng):**

```bash
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic configured-topic

kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name configured-topic --describe
# Dynamic configs for topic configured-topic are empty
```

**Bước 3 — thêm config `min.insync.replicas=2`:**

```bash
kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name configured-topic \
  --alter --add-config min.insync.replicas=2
# Completed updating config for topic configured-topic
```

Kiểm tra lại sẽ thấy:

```
Dynamic configs for topic configured-topic are min.insync.replicas=2
```

`kafka-topics.sh --describe` cũng hiện dòng `Configs: min.insync.replicas=2` — tức default `1` của broker đã bị override.

**Bước 4 — xóa config để về default:**

```bash
kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name configured-topic \
  --alter --delete-config min.insync.replicas
```

Describe lại: config biến mất, topic rơi về default broker.

> `kafka-configs.sh` còn quản lý được entity `brokers`, `users`, `clients`, `ips` — nhưng hãy đọc docs kỹ trước khi đụng broker-level vì có loại cần restart.

## 3. Trade-offs Và Cảnh Báo Production

| Quyết định | Được gì | Mất gì |
|---|---|---|
| `min.insync.replicas=2` + `acks=all` | Mất 1 replica vẫn không mất data | Produce chậm hơn, cần ít nhất 2 ISR alive nếu không sẽ `NotEnoughReplicas` |
| Override nhiều config/topic | Mỗi topic tối ưu đúng nhu cầu | Khó quản trị nếu không version hóa — phải lưu mọi override vào Git/Terraform |
| Dùng default cho tất cả | Đơn giản | Topic quan trọng và topic rác cùng độ bền — sai lầm đắt giá |

## Pitfalls / Best Practice

- **Pitfall: set `min.insync.replicas=2` trong khi `replication.factor=1`.** Topic sẽ không produce được vì không bao giờ đủ 2 ISR. Hai config này phải đi cùng nhau.
- **Best practice:** mọi `add-config` trên production đều phải qua code review và lưu vết (ai đổi, khi nào, vì sao). Config trôi nổi là nguyên nhân hàng đầu của "hôm qua còn chạy".

## Kết Luận

Tóm lại: **default broker chỉ là fallback — topic quan trọng phải override bằng `kafka-configs.sh --alter`, verify bằng `--describe`, và version hóa mọi thay đổi.**

Biết đổi config rồi, muốn hiểu config retention/compaction chạy trên cái gì thì phải xuống tầng file. Bài tiếp theo mổ **segments và indexes** — nền vật lý của mọi topic.
