So first of all, we know that we have auto scaling
for Aurora in terms of the storage,
and so when we have instances of Aurora,
we have one writer instance and many read replicas.
So the writer instance is always accessible
using the writer endpoint.
The reason is that if the writer instance goes down,
another Aurora instance may be promoted as the writer,
and so therefore the writer endpoint would be updated.
As for the reader endpoint, again it is updated based
on how many we replicas you have.
So say for example,
you receive many requests and the load is spread
between two Amazon Aurora reader instances.
If the CPU usage goes up,
we can set up replicas auto scaling,
in which case two more replicas will be added
and the reader endpoint will be automatically updated
and extended to ta1ke into account these two new replicas.
So bottom line is, here,
what we need to remember is that the clients must connect
to the writer endpoint to find the writer replica,
and must connect to the reader endpoint
to find the reader replicas.
Aurora also has the concept of global databases.
So you have two ways of doing it.
Either you use the Aurora Cross Region Read replicas,
and they're very helpful for disaster recovery
and very simple to put in place,
or you just use the feature named Aurora Global Database.
That's recommended because one of the region will be defined
as the primary region,
which will take all the read and the write loads.
And then you will have up to 10 secondary read-only regions,
and the replication lag will be less than one second.
You can also set up within each secondary region
up to 16 read replicas,
which is very helpful for decreasing latency.
On top of it, in case of a disaster, you have an RTO
of less than one minute by promoting another region,
and on top of it, typical cross-region replication will take
less than one second.
So how does that work?
Well, we have a primary region
where the applications can do read and writes,
