So, let's talk about redeploys and rollbacks.
So, a rollback is when CodeDeploy actually redeploys
a previously deployed version of your application.
And a rollback can happen in the following cases.
Either it's automatic because, for example,
we have failed to deploy to a new EC2 instance
or ECS task or whatever.
Or we have linked a CloudWatch Alarm
and the CloudWatch Alarm got triggered.
Or you can have manual rollbacks if you wanted to.
Now, you can also disable rollbacks
and say that no matter what happens,
do not perform a rollback.
If a rollback happens, just remember that CodeDeploy
is going to go ahead and initially issue
a new deployment of the last known good version.
It's not a restored version.
Now, you need to know a little bit of things
about CodeDeploy troubleshooting.
So, in case you see this invalid signature exception,
that's because there is a time mismatch
between CodeDeploy and the EC2 instances
because we need accurate time references.
And so if the date and time on your EC2 instances
are not set correctly, you may see this kind of error.
So, the solution to this is just to synchronize the time
between your EC2 instance and for example,
the time provided by AWS.
So, sometimes the deployment or life cycle events
are going to be skipped and we're going to get
some of these errors such as the overall deployment failed
because too many individual instances failed deployment,
or too few healthy instances are available for deployments.
Or some instances in your deployment groups
are experiencing problems such as health constraints.
Then, you may have a few problems.
So, make sure that the CodeDeploy agent
is installed and running.
Then, make sure that the Service Role
or the IAM instance profile have the required permissions.
If you are using an HTTP Proxy,
make sure the CodeDeploy agent
is running with the proxy_uri parameter.
And make sure the date and time mismatch
is good between CodeDeploy and the agent.
So, just some normal troubleshooting.
On top of it, any kind of deployment failures
from CodeDeploy can also be intercepted using EventBridge.
If you have a deployment to an ASG,
and then the ASG has a scale out event,
meaning that new instances are added during the deployment.
Well, it turns out that the scale out event
will deploy the V1 version
because the new deployment has not finished being done.
And so, you may come into a case where the ASG
will have V1 and V2 versions of your application.
But don't worry, by default,
after a successful deployment onto an auto-scaling group,
CodeDeploy is going to automatically start
a follow on deployment
to update any outdated instance from V1 to v2.
Usually going to have some time
where you're running both versions at the same time.
Then, we have Blue-Green deployments and it turns out
that the allow traffic step is failing.
So, the app was correctly installed,
but the traffic cannot be allowed.
So, what happens because we don't see any errors
in the deployment logs?
Well, that may be because the ELB
has inconfigured or misconfigured health checks.
And so you need to review the health checks of the ELB,
make sure they are correct.
And of course, if the ELB health checks are not correct,
then traffic cannot be allowed to the EC2 instances.
But if the health checks are passing and correct,
then traffic can be allowed from the ELB
to the new EC2 instances.
