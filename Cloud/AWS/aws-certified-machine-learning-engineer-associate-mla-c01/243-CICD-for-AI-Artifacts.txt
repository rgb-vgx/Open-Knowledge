Let's talk about how continuous integration and deployment applies to AI artifacts.
It's really not much different from code, except that the artifacts themselves are different, right?
So, and they might be stored in version in different places.
So in AI, we have version artifacts beyond just the source code of the application itself.
We have things like prompt templates and prompt versions, and those might be managed by Amazon
Bedrock Prompt Management, potentially.
We have the models themselves.
If you're deploying actual models that you've tuned or trained yourself, you might be storing
those and versioning them in SageMaker Model Registry and MLflow.
If you're using agents and developing agents and configuring them, you might be using Bedrock
Agent Core for that.
Versions and aliases under that, and when we talk about Bedrock Agents, by default,
we're talking Agent Core these days, not the Bedrock Agent Classic product that's been
put into maintenance mode.
Also knowledge bases and their configuration for retrieval.
Those might also be versioned alongside your app as well.
So whether it's source code for your actual application itself, prompt templates and versions,
the actual machine learning models and custom foundation models you might have, your agents
and the configuration for those agents, and your knowledge bases configurations.
These are all different artifacts that are specific to AI, but from a CI, CD standpoint,
it's treated just like code.
Now every one of these artifacts, just like code, will have its own version history and
its own registry that your pipeline can pull from.
So just like code, you're going to handle these AI artifacts as part of your deployment pipeline.
Code pipeline or code build can orchestrate builds and automate your tests and run evaluations
and deployments too.
Now a quick note here, it is important that you're not allowing your AI system to manage
this whole thing itself.
You don't want your AI system controlling its own tests and writing its own test code
and writing its own evaluations because it could cheat.
You know, it could say, oh, okay, I'm just going to loosen up this test because I'm not
passing it and that way I can pass it.
So it's important to make sure that those tests and evaluations are things that you
wrote and that they're sitting outside of where the AI can actually reach them.
Now once you actually do have something tested, only the approved and registered versions
that result are going to be promoted to production.
Otherwise you're going to kick it back and try again.
And you know, you're going to build them, package your stuff up, run your tests and evaluations.
If it passes, you're going to register it and version it and then push it out.
And if something goes horribly wrong, you can have a mechanism hopefully to roll back
to an earlier known good version if they actually got that far.
Ideally that test and evaluation phase would have caught it though, right?
So CICD and the whole concept of AI ops isn't really all that different from traditional
CICD for pushing out applications.
It's just that the artifacts are different.
You're not limited to code.
You have these other artifacts for AI in the mix as well.
