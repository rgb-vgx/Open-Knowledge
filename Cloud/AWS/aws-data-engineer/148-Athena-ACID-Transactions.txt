Instructor: A new feature in Athena
is ACID transaction support.
That means that we have strict guarantees
about transactions.
So you can actually have concurrent users hitting the same
row at the same time and have it all work consistently.
Under the hood is powered by Apache Iceberg.
And to use it, all you need to do is add
table_type equals ICEBERG when you're creating
a new table in Athena using the Create Table command.
And this allows you, like I said,
to have concurrent users safely making
row level modifications or deletions, whatever it is,
without worrying about them stomping on each other.
This is actually compatible with Elastic Map Reduce,
Apache Spark and anything that supports
the Apache Iceberg table format.
The good thing is that it removes any need
for custom record locking.
So without ACID support, you would need to have some sort
of a solution for locking a record
and unlocking it surrounding any modifications to it
so that if two people were hitting the same record
at the same time and trying to write to it,
they wouldn't be fighting with each other.
Iceberg and ACID transactions
just does that for you automatically now.
Also a little side benefit
is that it gives you what's called time travel operations.
So you actually have the ability to recover data
that was recently deleted,
just using a plain old select statement.
So some of the historical data that is keeping around
for the purpose of ACID transactions
can be used for that purpose.
Now remember when we talked about governed tables
in Lake Formation?
Well, this is kind of another way of doing the same thing.
So governed tables gave us ACID support on S3 tables
in Lake Formation, but this is another way
of getting acid features with Athena.
So you could set up a governed table in Lake Formation
and then hit that table with Athena,
and you would have ACID support.
This is just another way of doing it.
So you can just create a table explicitly
from Athena directly with a table type of Iceberg,
and you'll get ACID support on that as well.
So kind of two different ways
of solving the same problem there.
Now, you might also remember that in Lake Formation
with governed tables, it had a feature
to automatically compact those tables over time,
because over time there's sort of this overhead
that builds up and it can actually make your performance
degrade as time goes on.
Now with Athena ACID, at least for now,
you do need to do that yourself periodically.
So if you are using acid transactions in Athena,
you'll probably wanna do a command like this
once in a while.
Optimize table, rewrite data using BIN_PACK
where a catalog equals whatever.
So a command like that will go back
and compact your data that's sort of been bloated
by this ACID support over time and make it performant again.
So that's the kind of thing
I could see showing up on the exams,
that kind of trivia.
What do you do if your ACID transactions
are getting slower over time?
Well, the answer would be
