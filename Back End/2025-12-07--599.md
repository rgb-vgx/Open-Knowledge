**Long Polling** là một biến thể thông minh của Polling, được sinh ra để mang lại trải nghiệm gần thời gian thực (near real-time) mà không cần duy trì kết nối phức tạp như WebSocket, đồng thời tránh lãng phí băng thông mạng do Polling ngắn gây ra.

Đây là pattern nổi tiếng được sử dụng bởi các hệ thống phân tán lớn như **Apache Kafka** cho các Consumer (bên tiêu thụ dữ liệu) của mình.

## 1. Vấn đề của Short Polling và Giải pháp Long Polling

Như chúng ta đã biết, **Short Polling** yêu cầu Client phải liên tục hỏi Server, ngay cả khi Server biết chắc chắn rằng kết quả chưa sẵn sàng.

- **Server phản hồi ngay:** *"Chưa có gì đâu."*
- **Chi phí:** Lãng phí tài nguyên CPU (Server) và băng thông (Network) cho 99% request trả về kết quả "Không".

**Long Polling** thay đổi cách Server phản ứng:

> Client gửi request hỏi, nhưng thay vì phản hồi ngay lập tức nếu chưa có dữ liệu, Server sẽ **giữ kết nối mở (Hold Connection)** và chỉ phản hồi khi:
> 
> 1. Dữ liệu đã sẵn sàng.
> 2. Đã hết thời gian chờ tối đa (Timeout).

Sau khi nhận được phản hồi, Client ngay lập tức gửi một yêu cầu Long Polling mới.

## 2. Cơ chế hoạt động của Long Polling

Long Polling hoạt động như một cầu nối giữa Short Polling và Push Model:

1. **Submit Request:** Client gửi request Long Polling (ví dụ: `GET /checkstatus?jobId=...` hoặc `GET /topic?offset=...`).
2. **Server Blocking (Chặn):**
   - **Nếu dữ liệu CHƯA sẵn sàng:** Server **KHÔNG** đóng kết nối ngay. Server sẽ đặt request này vào một trạng thái chờ (Pending queue) và bắt đầu một bộ hẹn giờ (Timeout).
   - **Nếu dữ liệu đã sẵn sàng (Event arrives):** Server ngay lập tức xử lý request đang chờ, trả về dữ liệu và đóng kết nối.
3. **Timeout:** Nếu dữ liệu chưa sẵn sàng nhưng thời gian chờ đã hết (ví dụ: 30 giây), Server trả về phản hồi rỗng hoặc thông báo hết giờ và đóng kết nối.
4. **Loop:** Client nhận phản hồi và ngay lập tức gửi một yêu cầu Long Polling mới.

### Ví dụ thực tế: Kafka

Consumer trong Kafka sử dụng Long Polling để tiêu thụ dữ liệu từ Topic:

1. Consumer gửi request: *"Tôi muốn dữ liệu mới nhất từ Topic X, Offset Y."*
2. **Nếu Topic KHÔNG có dữ liệu mới:** Kafka giữ kết nối đó mở cho đến khi có Producer (bên sản xuất) gửi dữ liệu mới vào Topic đó.
3. **Nếu Topic CÓ dữ liệu mới:** Kafka ngay lập tức trả lời Consumer bằng các message đó.

Điều này đảm bảo Consumer chỉ tạo ra lưu lượng truy cập khi thực sự có dữ liệu để lấy, giảm đáng kể lưu lượng dư thừa.

## 3. Ưu và Nhược điểm

| **Ưu điểm (Pros)**                                                                   | **Nhược điểm (Cons)**                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Giảm tính "Chatty":** Giảm thiểu số lượng request đáng kể so với Short Polling.    | **Không hoàn toàn Real-time:** Vẫn có độ trễ (latency) nhỏ, tối đa bằng thời gian timeout. Nếu event xảy ra ngay sau khi Client vừa gửi poll, Client vẫn phải đợi đến khi kết nối tiếp theo được gửi đi.                     |
| **Thân thiện với Backend:** Server không bị dồn dập bởi các request kiểm tra vô ích. | **Tốn tài nguyên Server (Connections):** Server phải giữ rất nhiều kết nối mở đồng thời trong trạng thái chờ. Điều này đòi hỏi Web Server phải có khả năng xử lý nhiều I/O bất đồng bộ (như Node.js, Go, Nginx, Netty/Java). |
| **Giảm băng thông:** Giảm thiểu việc gửi đi các HTTP header lặp đi lặp lại.          | **Phức tạp hơn:** Việc quản lý các request đang chờ, logic timeout, và xử lý khi dữ liệu đến (thay đổi trạng thái từ Blocked sang Responding) phức tạp hơn Short Polling.                                                    |

## 4. Thực hành: Long Polling Server

Chúng ta sẽ mô phỏng việc giữ kết nối cho đến khi tác vụ được hoàn thành (hoặc gần hoàn thành).

### Kịch bản

1. **POST /submit**: Tạo job mới, trả về `jobId`.
2. **GET /check?jobId=...**: Server sẽ **treo kết nối** cho đến khi tiến độ đạt 100% (hoặc Timeout).

### 4.1. Node.js (Express)

Node.js rất phù hợp cho Long Polling nhờ Event Loop của nó, cho phép xử lý nhiều kết nối đang chờ (I/O Bound) mà không chặn luồng chính.

```
const express = require('express');
const app = express();
const PORT = 8080;

// Bộ nhớ tạm lưu trữ các jobs và các Client đang chờ
const jobs = {};
const pendingClients = {}; // Key: jobId, Value: Array of response objects (res)

// Giả lập xử lý job
function startJobProcessing(jobId) {
    let progress = 0;
    const interval = setInterval(() => {
        progress += 10;
        jobs[jobId] = progress;
        console.log(`Job ${jobId} Progress: ${progress}%`);

        if (progress >= 100) {
            clearInterval(interval);
            // KHI JOB XONG: PUSH kết quả cho tất cả clients đang chờ
            if (pendingClients[jobId]) {
                pendingClients[jobId].forEach(res => {
                    res.json({ jobId: jobId, progress: 100, status: "Completed" });
                });
                delete pendingClients[jobId]; // Dọn dẹp
            }
        }
    }, 3000);
}

// 1. Endpoint gửi yêu cầu xử lý
app.post('/submit', (req, res) => {
    const jobId = `job:${Date.now()}`;
    jobs[jobId] = 0;
    startJobProcessing(jobId);
    res.json({ jobId: jobId, status: "Job created" });
});

// 2. Endpoint Long Polling
app.get('/checkstatus', (req, res) => {
    const jobId = req.query.jobId;

    // 1. Kiểm tra ngay lập tức
    if (jobs[jobId] === 100) {
        return res.json({ jobId: jobId, progress: 100, status: "Completed" });
    }

    // 2. Nếu chưa xong: THÊM client vào hàng đợi và GIỮ kết nối
    if (!pendingClients[jobId]) {
        pendingClients[jobId] = [];
    }
    pendingClients[jobId].push(res);

    // Thiết lập Timeout (để kết nối không treo mãi mãi)
    req.setTimeout(35000, () => { // 35 giây timeout
        if (jobs[jobId] < 100) {
            // Trả lời nếu timeout trước khi hoàn thành
            res.json({ jobId: jobId, progress: jobs[jobId] || 0, status: "Timeout, please poll again" });

            // Xóa client khỏi danh sách chờ sau khi timeout
            pendingClients[jobId] = pendingClients[jobId].filter(client => client !== res);
        }
    });
});

app.listen(PORT, () => console.log(`Long Polling Server running on port ${PORT}`));
```

### 4.2. Java (Conceptual Spring Boot)

Trong Java, Long Polling thường được xử lý bằng `DeferredResult` (trong Spring WebFlux hoặc Servlet 3.0+ Asynchronous) để giữ kết nối HTTP mà không cần chặn luồng chính của Container.

```
/* Spring Boot Code Snippet (Conceptual) */
import org.springframework.web.bind.annotation.*;
import org.springframework.web.context.request.async.DeferredResult;
import java.util.concurrent.*;
import java.util.*;

@RestController
public class LongPollingController {

    private Map<String, Integer> jobProgress = new ConcurrentHashMap<>();
    // Lưu các yêu cầu đang chờ: Key là Job ID, Value là List các DeferredResult
    private Map<String, List<DeferredResult<Map<String, Object>>>> pendingResults = new ConcurrentHashMap<>();

    // Giả lập background task
    @PostConstruct
    public void startJobMonitor() {
        Executors.newSingleThreadScheduledExecutor().scheduleAtFixedRate(() -> {
            jobProgress.keySet().forEach(jobId -> {
                int currentProgress = jobProgress.getOrDefault(jobId, 0);
                if (currentProgress < 100) {
                    int newProgress = Math.min(100, currentProgress + 10);
                    jobProgress.put(jobId, newProgress);

                    if (newProgress == 100) {
                        // KHI JOB XONG: PUSH kết quả cho DeferredResult đang chờ
                        if (pendingResults.containsKey(jobId)) {
                            List<DeferredResult<Map<String, Object>>> results = pendingResults.remove(jobId);
                            Map<String, Object> finalResult = Map.of("jobId", jobId, "progress", 100, "status", "Completed");
                            results.forEach(dr -> dr.setResult(finalResult));
                        }
                    }
                }
            });
        }, 0, 3, TimeUnit.SECONDS); // Cập nhật mỗi 3 giây
    }

    @PostMapping("/submit")
    public Map<String, String> submitJob() {
        String jobId = UUID.randomUUID().toString();
        jobProgress.put(jobId, 0);
        return Map.of("jobId", jobId, "status", "Job Started");
    }

    @GetMapping("/checkstatus")
    public DeferredResult<Map<String, Object>> checkStatus(@RequestParam String jobId) {
        // Thiết lập timeout 30 giây
        DeferredResult<Map<String, Object>> deferredResult = new DeferredResult<>(30000L, 
            Map.of("jobId", jobId, "status", "Timeout, re-poll."));

        // Kiểm tra ngay
        if (jobProgress.getOrDefault(jobId, 0) == 100) {
            deferredResult.setResult(Map.of("jobId", jobId, "progress", 100, "status", "Completed"));
            return deferredResult;
        }

        // Đăng ký DeferredResult vào danh sách chờ
        pendingResults.computeIfAbsent(jobId, k -> new CopyOnWriteArrayList<>()).add(deferredResult);

        // Xóa khỏi danh sách chờ khi timeout hoặc hoàn thành
        deferredResult.onCompletion(() -> {
            List<DeferredResult<Map<String, Object>>> list = pendingResults.get(jobId);
            if (list != null) {
                list.remove(deferredResult);
            }
        });

        return deferredResult; // Kết nối bị treo (Deferred)
    }
}
```

### 4.3. Go (Golang)

Go sử dụng `channels` để giao tiếp giữa background goroutine (nơi xử lý job) và HTTP handler (nơi giữ kết nối).

```
package main

import (
    "encoding/json"
    "fmt"
    "net/http"
    "sync"
    "time"
)

type JobStatus struct {
    Progress int
    ResCh    chan []byte // Channel để gửi kết quả hoàn thành
}

var jobs = make(map[string]*JobStatus)
var mu sync.Mutex

func startJob(jobID string) {
    status := &JobStatus{
        Progress: 0,
        ResCh:    make(chan []byte, 1), // Channel để gửi kết quả hoàn thành
    }

    mu.Lock()
    jobs[jobID] = status
    mu.Unlock()

    go func() {
        for i := 0; i <= 100; i += 10 {
            time.Sleep(3 * time.Second)
            mu.Lock()
            status.Progress = i
            mu.Unlock()

            if i == 100 {
                result, _ := json.Marshal(map[string]interface{}{"jobId": jobID, "progress": 100, "status": "Completed"})

                // Gửi kết quả qua channel để mở khóa handler đang chờ
                status.ResCh <- result 
                close(status.ResCh)
                break
            }
        }
    }()
}

func submitHandler(w http.ResponseWriter, r *http.Request) {
    jobID := fmt.Sprintf("job-%d", time.Now().UnixNano())
    startJob(jobID)

    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(map[string]string{
        "jobId": jobID, 
        "status": "Job Created",
    })
}

func checkStatusHandler(w http.ResponseWriter, r *http.Request) {
    jobID := r.URL.Query().Get("jobId")

    mu.Lock()
    status, exists := jobs[jobID]
    mu.Unlock()

    if !exists {
        http.Error(w, "Job not found", http.StatusNotFound)
        return
    }

    // Thiết lập Timeout: Cho phép chờ tối đa 35 giây
    timeout := time.After(35 * time.Second)

    select {
    case result := <-status.ResCh:
        // 1. Nhận kết quả qua channel -> Job đã xong
        w.Header().Set("Content-Type", "application/json")
        w.Write(result)
    case <-timeout:
        // 2. Timeout xảy ra -> Trả về trạng thái hiện tại
        mu.Lock()
        currentProgress := status.Progress
        mu.Unlock()

        response, _ := json.Marshal(map[string]interface{}{
            "jobId": jobID, 
            "progress": currentProgress, 
            "status": "Timeout, re-poll."})

        w.Header().Set("Content-Type", "application/json")
        w.Write(response)
    }
}

func main() {
    http.HandleFunc("/submit", submitHandler)
    http.HandleFunc("/checkstatus", checkStatusHandler)
    fmt.Println("Server running on :8080")
    http.ListenAndServe(":8080", nil)
}
```

## 5. Kết luận

**Long Polling** là một giải pháp cân bằng tuyệt vời, giúp chúng ta đạt được hiệu suất gần Real-time mà vẫn giữ được sự đơn giản của giao thức HTTP Request/Response. Nó loại bỏ sự lãng phí tài nguyên của Short Polling, biến việc chờ đợi từ Client sang Server, nơi việc quản lý các I/O đang chờ được thực hiện hiệu quả hơn (đặc biệt trong các môi trường hỗ trợ I/O bất đồng bộ như Go và Node.js).
